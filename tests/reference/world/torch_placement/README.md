# Ordinary Torch support lifecycle

Two fresh ordinary OpenJDK 17 VMs execute 193 declared calls on genuine
registered Torch 50. The unchanged original seven VM methods are can-place,
private floor support, placed-face, onAdded, private validation/removal,
neighbor change, and tick. The inherited UU face wrapper and actual FD World
placement wrapper are also entered. Private methods are invoked reflectively;
their original Code is unchanged. No original class/body is replaced or
recompiled. This is support/lifecycle evidence, separate from Torch geometry.

`profiles.tsv` and `protocol.json` freeze the complete case order and fields.
They cover horizontal/floor/Fence supports, rejected supports, first-supported
orientation, clicked-face overrides, metadata-zero ticking, support-loss
drop/removal, signed read-only coordinates, NULL World, and NULL formal tick
Random. All nine reached NULL-World exceptions remain literal failures.
The other outcomes are 54 false, 40 true, and 90 void returns. This matrix has
no authored callback refusal; native callback failures need separate controls.

Each VM constructs one genuine fd World and four canonical saved Chunks using
the existing Torch/picking fixture and seed-23 saved inputs. There is no App,
Player, Timer worker, GUI, or native library. The World, actors, and lighting
queue persist across the ordered cohort. Before each profile, only the declared
five arrays and Chunk `i/n` fields are reset: Blocks/Data/BlockLight/HeightMap
zero, SkyLight byte `0x0f`, `i=0`, `n=true`; direct support/target stores follow.
No World setter is used for authoring, and no queue is reset or drained.
Signed-coordinate cases are read-only, so no rejected/unpublished Item
constructor is omitted from the entropy observations.

The complete logical `TORCH` JSON rows retain result/exception, center states,
all sparse byte changes across five arrays/four Chunks, the complete ordered
light queue before/after, ordered WorldAccess callbacks, and actual published
Item Stack/default fields. All 193 rows and `COMPLETE\t193` match literally
between the two VMs. The original has 83 changed-byte records, at most two
queued light regions, and actual cell/add callbacks. No game behavior is
computed by the capture helper as an expected-value oracle.

Raw stdout is **not** equal between the VMs. Each process retains every actual
`ENTROPY` row, including World Random pre/post seed/Gaussian fields and each
published Item's raw position, velocity, yaw, bob phase, genuine default Entity
Random state, and actual post-constructor Math Random state. Source clocks,
Random states, phases, and input are never reset, seeded, or replaced. There
is no constructor-entropy equality or entropy-distribution claim across VMs
or engines. Logical drop/publication events remain in the compared rows;
random-dependent raw values are explicitly retained in the separate audit.

`entropy.py` independently audits each actual stream with Python Java-LCG and
binary32/binary64 arithmetic. Each process publishes 34 Torch Items and passes
136 World nextFloat steps and 272 Math LCG steps. The probability draw and
three drop-offset floats are checked against the same process's World stream.
The actual Item bob/yaw/velocity formulas are checked by reversing eight steps
from its observed post-Math state, then replaying four nextDouble draws. Later
pre/post states must join the actual ordered cohort. The **first Math prestate
is unobserved**; its predecessor is an inference for formula auditing only.
The helper reads the Math holder only after an actual original HL constructor
has already used it. It does not warm or probe that owner's initial phase.
Default Entity Random seeds are recorded without predicting their constructor
entropy; only their source-default Gaussian cache is checked.

bytes, protected by `-text` and the repository's CR whitespace policy.
`original.stdout` is the declared LF selection of **every** TORCH/COMPLETE
